# The guard

`guard.py` is a Claude Code `PreToolUse` hook: a program Claude Code runs before every tool call. It can block the call by exiting with code 2, and the reason it prints is shown to Claude. It uses only the Python standard library.

It has two profiles. The profile is chosen only by the command line the hook is installed with, never by an environment variable, so the agent cannot switch it from a tool call.

| Profile | For | Install |
|---|---|---|
| `cloud` (the default) | the nightly cloud routine | `python -m scout init-data` copies it into the private data repo |
| `agent` | a local agent on your own machine | `settings.agent.json`, below |

`python3 guard.py --version` prints `guard 1`, so an installer can check which copy is in place.

## What it blocks

**Both profiles** (the scout reads GitHub and never writes to it):

- `gh` writes (`gh pr/issue create|comment|review|merge|...`, `gh repo fork`, `gh release`, `gh label`, `gh auth`, ...), and `gh api` with a write method, body fields or a GraphQL mutation
- `curl`, `wget` and scripted HTTP writes to GitHub
- changing git remotes or rewriting remote URLs through `git config`
- GitHub MCP tools that are not read verbs (`get`, `list`, `search`, `read`, `view`, `fetch`, `download`, `show`, `check`)

**`cloud` only:** one write is allowed, `git push origin claude/scout-data` from the checkout of the `oss-scout-data` repo.

**`agent` adds** (all of the above, plus the rules below). It errs on blocking:

- **Text rules.** The agent profile reads the whole command as plain text, without trying to understand the shell, so pipes, heredocs, `$( )`, backticks, `{ }`, `if` and `sh -c` all look the same to it. A command is blocked if its text contains any of these:
  - `git` and `push` as separate words anywhere (`git push`, `git -C x push`, `git 2>&1 push`, `echo 'git push' | sh`, `git submodule foreach git push`, `git subtree push`, `git rebase -x 'git push'`, a Python script that runs `["git", "push"]`), or the words `git-push`, `send-pack`, `http-push`, `receive-pack` (also with `git-` in front), or `alias.` starting a word (any case) together with the word `git` (a git alias on the command line or in `git config`; `src/alias.py` does not count), or `GIT_CONFIG_PARAMETERS` or `GIT_CONFIG_KEY_`. The message is "pushes are done by the owner, not the agent".
  - `sudo`, `sudoedit`, `doas`, `pkexec` or `run0` as words.
  - `socat`, `--unix-socket`, `UNIX-CONNECT`, `UNIX-CLIENT` or `UNIX-SENDTO`, or `nc`, `ncat` or `netcat` together with a `-U` flag (also inside a combined flag such as `-Uv`).
  - Holt's folders, by their path words rather than exact paths: `holt` as a whole word (a path part or a word of its own) together with one of `etc`, `run`, `lib`, `srv` or `var` as a whole word, anywhere in the command. This covers `/etc/holt`, `/etc//holt`, `/etc/./holt`, `../../etc/holt`, `/tmp/../etc/holt`, `/var/run/holt`, `cd / && cat etc/holt/x`, `cd /var && cat lib/holt/x` and `cd /etc && cat holt/credentials/x`. `~holt` as a whole word counts too (it is the home of the `holt` user, `/var/lib/holt`), and so does a path written with `%2F` for `/` (`http+unix://%2Frun%2Fholt%2Fweb.sock`). `~/holt-notes`, `~holtz`, `/srv/holt-src` and `/etc/holt.d` pass, because they are other words. Accepted false positives: `ls tests/fixtures/etc/holt`, or any command that has the words `run` and `holt` (`cargo run -p holt`).
  - `credentials` together with `run`, both as whole words (`/run/credentials`, `/var/run/credentials/x`, `ls ../../run/credentials`), and `CREDENTIALS_DIRECTORY`.
  - `holt` or `credentials` as a word at all, when the session's folder is `/` or is in or below `/var`, `/run`, `/etc` or `/srv` (`ls credentials` in `/run`, `ls ../holt` in `/etc/ssl`).
  - **GitHub writes as words.** The word `gh` (any case, also `gh.exe`) together with any word that names a write: `create`, `new`, `comment`, `review`, `merge`, `close`, `reopen`, `edit`, `delete`, `fork`, `ready`, `lock`, `unlock`, `transfer`, `archive`, `unarchive`, `rename`, `sync`, `set`, `upload`, `enable`, `disable`, `cancel`, `rerun`, `pin`, `unpin`, `develop`, `remove`, `revert`, `update-branch`, `approve`, `login`, `logout`, `refresh`, `stop`, `link`, `unlink`, `copy`, the `gh project` item and field writes, `secret`, `variable`, `ssh-key`, `gpg-key` or `deploy-key`; or `gh` with `workflow` and `run`. Like `git` and `push`, the words may be anywhere and in any order, so `setsid gh pr create`, `strace gh pr create`, `gh pr -R o/r create`, `gh pr \` + newline + `create` and `echo gh pr create | sh` are all blocked.
  - `gh` with `api` and a write in any spelling: `-X`/`--method` with anything but `GET` (`-X POST`, `-XPOST`, `-X=POST`, `-iXPOST`, `--method=post`), body fields (`-f`, `-F`, `-fbody=x`, `--field`, `--raw-field`, `--input`) without `-X GET`, or `mutation`.
  - `http`, `https`, `xh`, `xhs` or `httpie` as a word together with a GitHub host (`github.com` or `githubusercontent`, any case). httpie and xh to GitHub are blocked outright.
  - Text piped into a shell (`| sh`, `| bash`, `|& zsh`, `| xargs bash -c`, `| sudo sh`, `| iex`), or fed to one with a heredoc, here-string or process substitution (`bash <<< ...`, `sh <<EOF`, `bash <(...)`, `source <(...)`). What the shell would run cannot be read. `source` counts only as the command itself, so `cat > source/foo.txt <<'EOF'` passes.
  - Each text rule is checked twice: on the text as given, and with quote marks, backslashes and `\` line continuations removed, so `g'i't pu\sh` and `s""udo` count too.
- **The words are enough, even in harmless text.** A command that only mentions `git` and `push`, or `sudo`, is blocked: `git commit -m 'fix the git push bug'`, `git log --grep=sudo`. Write such text into a file and use `git commit -F file`. `git stash push` is blocked too, by the `git` and `push` rule: use `git stash`. `cat /usr/local/lib/holt/guard/README.md` is blocked in Bash because the path has `holt` and `lib`, but the `Read` tool can open it. The same goes for `gh` with a write word: `gh pr list --search create`, `gh pr list --search new`, `set -e; gh pr list` (`set`), `gh issue view 1 && npm run stop` (`stop`) and `gh workflow view ci && npm run build` (`workflow` and `run`) are blocked. Also blocked: `gh api` in a command that has `-f` somewhere else (`gh api x && curl -fsSL ...`), a regex such as `grep -E 'zsh|bash'` (the quoted text is read as a command too, so it looks like a pipe into `bash`), `curl ... | sh` installers, and `http` next to a GitHub host in any text.
- **GitHub writes behind a wrapper or in quotes.** The cloud rules above are also run on the commands inside `sh -c`/`bash -c`/`zsh -c`/`dash -c` (also `bash -c -- '...'`), `eval`, `$( )`, backticks, every `find -exec`/`-execdir`/`-ok` (each one is read once), and after `env`, `timeout`, `nice`, `ionice`, `setsid`, `nohup`, `time`, `exec`, `command`, `xargs` (also `xargs -I{}`), `stdbuf`, `strace`, `ltrace`, `unbuffer`, `chronic`, `if`/`then`/`do`, `{` and `!`. `\` line continuations are joined first, and a redirect's target goes with it even when quoted (`gh >'/dev/null' pr create`). `gh`, `curl`, `wget`, httpie and `git` are also looked for anywhere in a simple command, so an unknown wrapper in front (`strace -f curl ...`, `flock /tmp/git git remote set-url ...`) does not hide them. Every such word is checked, and a command with more than 16 words naming the same one of them is blocked unread. Every quoted string (`'...'`, `"..."`, `$'...'`) is checked as a command too, wherever it is, and so is the text between any two quote marks, in case the quoting is read wrong. So `bash -c 'gh pr create ...'`, `timeout 5 gh pr create ...`, `echo 'gh pr create' | sh`, `sh <<< 'gh pr create'`, `env -S 'gh pr create'` and `echo "$(gh pr create)"` are blocked, and so is a harmless command that quotes a GitHub write (`grep "gh pr create" notes.md`). (Only the agent profile does this; the cloud profile is the same as it always was.)
- **More GitHub writes.** `gh pr new`, `gh issue new` and `gh repo new` (`new` is gh's alias for `create`), and `-R`/`--repo`/`--repo=` anywhere in a `gh` command. To GitHub hosts, in any case (`https://API.GITHUB.COM`): `wget --method`, `--post-data`, `--post-file`, `--body-data` and `--body-file`, curl's `--data...`, `--form...`, `--json`, `--upload-file` and `--request=...`, and curl's short flags read as a cluster (`-sSXPOST`, `-sSd '{}'`). The cluster ends at an option that takes a value, so `curl -ADevTools` (a user agent) and `curl -odraft.json` (an output file) pass. A method other than `GET` or `HEAD` blocks. The GitHub host may be anywhere on the command line, so `echo https://api.github.com/... | xargs curl -X POST -d '{}'` is blocked too, and so is a harmless line that names a GitHub host and posts somewhere else (`git clone https://github.com/o/r && curl -d x localhost:8000`). A config file (`-K`, `--config`, for curl or wget) can hold a method or body for GitHub where the guard cannot see it (`-X POST`, `-d`, or the wget equivalent), so `-K` and `--config` are blocked on a line that names a GitHub host (`curl -K cfg https://api.github.com/...`, also `-K -`; `wget --config=cfg https://api.github.com/...`); to any other host they pass. wget's `-e`/`--execute` (`wget -e post_data=x ...`) is blocked the same way, and wget's long options may be shortened (`--exe`, `--meth`, `--me`), which blocks too. The scripted-write patterns (`requests.post(...)`, `urlopen(..., data=...)`, `method='POST'`) count with any GitHub host in any case (`https://API.GITHUB.COM`). `git remote add|set-url|rename` and `git config` with a `remote.`, `url.`, `pushurl` or `insteadOf` key are matched in any case (`git config REMOTE.origin.url x`) and after any git option.
- **Claude's own file tools.** `Read`, `Edit`, `MultiEdit`, `Write`, `NotebookEdit`, `NotebookRead`, `LS`, `Grep` and `Glob` are blocked when their path (`file_path`, `notebook_path`, `path`, and for `Glob` the `pattern`) is inside a Holt folder or `/run/credentials`, after relative paths are resolved against the session's folder and symlinks are followed (before `..` is removed, as the system does). `Grep`, `Glob` and `LS` without a `path` look in the session's folder, so that is checked too. `Grep`'s `pattern` is a regular expression, not a path, so it is not checked. `Glob`'s `pattern` and `Grep`'s `glob` are resolved against the folder they search (`glob: holt/**` with `path: /etc` is blocked), and also get the Holt and credentials text rules, with the session-folder rule applied to the folder they search: `Glob **/holt/**` from `/` or `/var` is blocked. They get no other text rules, since a pattern runs nothing: `Glob **/sudo/*.py` passes. The text of `Edit` and `Write` is not scanned.
- **Shell tools.** `Bash`, `Monitor` and `PowerShell` get all the checks above on their `command`, and are blocked without command text (missing, or not a string). Their `description` is not checked.
- **Text that cannot act on its own is not checked.** `TodoWrite`, `AskUserQuestion`, `ExitPlanMode` and `WebSearch` get no text rules at all, and neither do the `prompt` and `description` of `Task` and `Agent` (a subagent's own tool calls come through this hook too). So the agent can ask "Can you run git push origin fix?", plan "Owner runs git push", keep a todo "Fix sudo check" and search for "git push force-with-lease". Their other fields (`Task`'s `subagent_type`, for example) still get the text rules.
- **Every other tool** (MCP tools, `WebFetch`, a tool the guard has never heard of) gets the text rules, with the session-folder rule, on every string it is given (keys too), on all of its strings joined with spaces, and on its own name with `_` and `-` read as spaces. So `{"command": "git", "args": ["push", "origin", "main"]}`, `mcp__git__git_push` and `mcp__gh__create_issue` are blocked. Its command-like inputs (`command`, `cmd`, `script`, `argv` and `args`, as text or as a list of words, each on its own and all joined) also get the full shell checks, so `{"cmd": "curl -sSXPOST https://api.github.com/x"}` is blocked.
- **Any tool call at all** is blocked if the session's own folder is inside a Holt folder or `/run/credentials`.
- **A call it cannot check is blocked.** Unreadable or non-object JSON, an empty tool name, a tool name or input of the wrong type, a `Bash`, `Monitor` or `PowerShell` call without command text, a NUL byte in any string, any string longer than 100,000 characters, commands nested more than four levels deep, or any error while checking exits 2. (An error that exited 1 would let Claude Code run the tool.) Every pattern and parse it uses takes time in proportion to the text (each distinct command is checked once, each `find -exec` is read once, long runs of wrappers are counted, not copied, and `git`'s leading `-C`/`-c` options are stepped over, not copied), so a crafted command cannot make it run past the hook's timeout; crafted commands of about 99,000 characters (`git -c -c -c ...`, `git -C . -C . ...` among them) are decided in under a second each.
- **A hook that fails blocks too.** `settings.agent.json` sets `"onFailure": "block"` on the hook, so if Claude Code cannot start `python3` or the guard, the guard times out, or it exits with a code other than 0 or 2, the tool call is blocked. Without that setting Claude Code lets the call run. An older Claude Code that does not know `onFailure` ignores it and fails open.

A bad `--profile` value, `--profile` with no value, or any other argument blocks every tool call and exits 2 with a "Blocked by oss-scout guard" message, so a typo in the settings file stops the agent instead of loosening the guard.

## Limits

This is a speed bump for a well-behaved agent, not a sandbox. It is a hard stop only together with a separate user account that has no tokens, no GitHub login and no access to Holt's files. Blocking network access in general is a container concern, not the guard's.

What it does not catch, because it never runs anything:

- strings built at run time (`"gi"+"t pu"+"sh"`, `$(printf 'g%s' h)`, a variable that holds the command, `$X$Y`, `$'\x67h'`, a script written by one command and run by the next)
- config files that curl and wget read on their own (`~/.curlrc`, `CURL_HOME`, `~/.wgetrc`, `WGETRC`, or a `-K` file that holds the GitHub URL itself, or a `wget -i FILE` whose URLs are read from a file the guard does not open)
- globs and patterns for a path (`/etc/ho*`, `/etc/h?lt`)
- obfuscation such as base64 or hex that is decoded and run, unless it is piped or fed into a shell (`base64 -d | python3` still passes)
- a push or GitHub write made by a library inside a script, such as GitPython's `repo.remote().push()`, PyGithub or Octokit, `httpx.post(...)` or `fetch(..., {method: 'POST'})`, or any script file it is not shown
- a git alias for `push` that is already in a git config file, or a config file chosen with `GIT_CONFIG_GLOBAL`
- a GitHub write sent by a program the guard does not know, or by a script (it only reads `gh`, `curl`, `wget`, `http`/`xh` and a few Python patterns)
- a GitHub MCP server whose name does not contain "github" (`mcp__hub__open_issue`): the MCP rule goes by the name, so such a server's writes pass unless its name or inputs trip a text rule (`mcp__gh__create_issue` does: `gh` and `create`)
- a search of `/` or a parent of Holt's folders that does not name Holt (`Grep` for `token` with `path: /`, `grep -r token /etc`): only the operating system's permissions stop that

Because it reads text and not meaning, it also blocks some harmless commands (see above). That is on purpose.

## Install (agent profile)

Copy the `guard/` folder somewhere only root can write, for example `/usr/local/lib/holt/guard/`, then merge `settings.agent.json` into Claude Code's managed settings (on Linux, `/etc/claude-code/managed-settings.json`). The agent user must not be able to edit either one. The fragment sets the hook command to `python3 /usr/local/lib/holt/guard/guard.py --profile agent`, makes a failing hook block (`onFailure`), turns off the commit, pull request and session-link attribution, and also denies the same GitHub writes and `git push` in Claude's own permission list. Change the path in `command` if you install elsewhere.

## Test

```
/home/you/.cache/oss-scout-venv/bin/python -m pytest tests/test_guard.py      # or python3 -m pytest
python3 guard/guard.py --version                                               # guard 1
echo '{"tool_name":"Bash","tool_input":{"command":"git push origin main"}}' \
  | python3 guard/guard.py --profile agent; echo $?                            # block message, then 2
```

To try it in Claude Code: copy `guard/` to a temporary folder, make a throwaway project whose `.claude/settings.json` is `settings.agent.json` with the path in `command` pointed at that copy, and ask the agent to run `git push`. The call is blocked and the message is shown.
