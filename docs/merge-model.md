# Merge-prediction model

This page is regenerated by `scripts/train_merge_model.py` from the model it trains. The numbers below are from the last run.

**Verdict: the model does not beat the baselines, so the scout does not use it.** `use_merge_model` stays `false` in targets.toml; even if it is switched on, the scorer refuses a model file whose `beats_baseline` is false.

## The question

If an occasional outside contributor opens a pull request in this project, how likely is it to be merged within 90 days? The scout's `friendliness` score answers that with a hand-weighted mix of merge rate, time to merge, first-reply time and activity. This model checks whether a logistic regression trained on the scout's own pull request data does better, and only feeds the ranking if it clearly does.

## Features

Every input is known when the pull request is opened, or describes the project. Logins, names, URLs, labels, comments, reviews and text are never stored: `scout/prdata.py` keeps a fixed list of fields per PR in `pr_outcomes.jsonl`, and titles and bodies become lengths and two yes/no flags.

| Model input | From | Why |
| --- | --- | --- |
| author_prior_prs | `author_prior_prs_in_sample` | Earlier PRs by the same person in the project's sample. Returning contributors know the ropes. |
| log_title_len, log_body_len | `title_len`, `body_len` | log(1 + length). An empty description is a common reason for a quiet close. As of collection (see the leakage rules). |
| body_has_issue_ref | `body_has_issue_ref` | The description has `#123`, or a closing keyword (fixes/closes/resolves) with an issue link: work the project asked for. |
| weekend, hour_sin, hour_cos | `created_weekday`, `created_hour_utc` | When it was opened (UTC), as a weekend flag and a 24-hour cycle. |
| log_repo_prior_n, repo_prior_thin | `repo_prior_n` | How many outside PRs the project closed before this one was opened, and whether that is fewer than 5. |
| repo_prior_merge_rate | `repo_prior_merge_rate` | Share of those that were merged (empty below 5, then filled from the fit rows). |
| log_repo_prior_median_days | `repo_prior_median_days_to_merge` | Median days to merge among them (empty below 5). |
| stars_log10 | `stars_log10` | log10(1 + stars) at collection time. |
| cla, has_contributing | `cla`, `has_contributing` | The project asks for a CLA; it has a CONTRIBUTING file (at collection time). |
| language=…, owner_type=…, ai_policy=… | `language`, `owner_type`, `ai_policy` | One-hot; levels with fewer than 30 fit rows, missing and unseen values go to `other`. |

Numbers are standardized with the fit rows' mean and standard deviation. Stored but **not** model inputs:

| Field | Why it is left out |
| --- | --- |
| `author_assoc` | GitHub reports the association as it is now. A first-timer whose PR was merged is a CONTRIBUTOR afterwards, so the field partly records the outcome (in the initial exploratory run on real data, CONTRIBUTOR rows were merged about 55% of the time vs 11% for NONE). |
| `draft` | The current draft state. A PR has to leave draft before it can be merged, so a merged PR is never a draft (1 of 221 draft rows in the initial exploratory run was merged). |
| `title_wip_marker` | The current title. WIP markers are taken out before merging, the same problem as `draft`. |
| `from_fork` | Always true for an outside PR, so it carries no information. |

## Leakage rules

- **Label.** `y = 1` if the PR was merged within 90 days of being opened; closed without merging, merged later, or still open counts as 0.
- **Cut.** The cut is the newest collection time (2026-11-25 12:32 UTC). PRs opened within 90 days before it are left out, because their outcome isn't known yet. A PR closed after the cut counts as open at the cut.
- **Project record.** `repo_prior_*` is recomputed by `scripts/build_merge_dataset.py` from the same project's PRs closed strictly before this PR was opened. Changing a later PR's outcome cannot change an earlier row (tested). With fewer than 5 such PRs the rate and median are left empty and filled from the fit rows only.
- **Fills, levels and scaling** come from the rows being fit, never from the test split; the same holds inside each leave-one-project-out fold.
- **Static fields leak a little.** `stars_log10`, `language`, `owner_type`, `ai_policy`, `cla` and `has_contributing` are as of collection, not as of the PR. A project that added an AI policy or a CLA after a wave of rejected PRs, or that grew its stars, shows today's value on old rows. These change slowly, but they are one place the future reaches back.
- **PR fields are as of collection too.** The list API returns a PR as it is now. Titles, descriptions and flags can be edited during review. The fields that move with the outcome (`author_assoc`, `draft`, `title_wip_marker`) are kept out of the model (see above); title length, description length and the issue reference remain inputs and may carry a little of the same leak.

## The sample and its biases

- Rows come from what the nightly measurement already lists: each project's last 300 closed PRs **by update time** and its 100 newest open PRs. In a busy project an old PR is in that list only if something touched it lately, usually a late close, so old rows from busy projects would be mostly failures. To avoid that, a PR gets its first row only if it was opened after the point from which the lists hold every PR (`prdata.complete_since`). For busy projects that point is days or weeks back, so they contribute no rows until the nightly runs have collected 90 days and more; quiet projects reach years back. The dataset leans toward quieter projects for now.
- PRs that left the 100-newest-open window keep the last row seen; if an open PR's last `collected_at` is earlier than 90 days after it was opened, its horizon outcome is unknown and the dataset builder excludes it instead of labelling it 0.
- Optional PR size features (`additions`, `deletions`, `changed_files`) are not collected yet because they require one extra API request per pull request; rows without size are valid and the pipeline can add them later under a per-run budget.
- **Outside contributor** uses the scout's `is_outside` heuristic: from a fork, not a bot, author association NONE / FIRST_TIMER / FIRST_TIME_CONTRIBUTOR, or CONTRIBUTOR with fewer than 3 PRs in the sample. Staff with private org membership who work from forks and open few PRs still slip in; prolific outsiders are dropped. The 3-PR count uses the whole sample, including PRs opened later.
- Projects that merge outside GitHub (`merges_elsewhere`) and archived ones are excluded. The projects are the ones the scout watches (large, company-backed, mostly C, C++ and Python), not GitHub at large.

5370 rows in the file, 5370 outside rows in eligible projects, 3697 left out as too recent, **1673 in the dataset (760 merged in time) from 56 projects**.

## Split

Rows are sorted by (created_at, repo, number). The oldest 60% train, the next 20% validation, the newest 20% test. A boundary never falls between two rows opened at the same second, so every test row was opened after every train row.

| Split | Rows | Merged in time | First opened | Last opened |
| --- | ---: | ---: | --- | --- |
| train | 1004 | 520 | 2014-03-16 | 2026-03-22 |
| val | 334 | 113 | 2026-03-22 | 2026-06-30 |
| test | 335 | 127 | 2026-06-30 | 2026-08-26 |

C (inverse L2 strength) was chosen on validation AUC from 0.001, 0.003, 0.01, 0.03, 0.1, 0.3, 1, 3: **C = 0.01**. The test model and baselines B0/B1 are fit on the training split (60%) and scored on test once; each leave-one-project-out fold chooses C on an inner time split of the other projects so no held-out project influences tuning. Gradient boosting was not pursued because logistic regression did not leave clear headroom over the baselines on this sample size.

## Baselines

All scored on the same test rows and in the same leave-one-project-out folds.

- **B0**: constant: the merge rate of the training split.
- **B1**: the project's own merge rate in the training split (the training rate when it has fewer than 5).
- **B1_prior**: the project's raw historical merge rate over its PRs closed before this one was opened (the training rate when fewer than 5; uses any-time merges, while the label y is 90-day merges).
- **B2**: the merge-record part of the scout's friendliness: (0.45 * merge rate + 0.25 * speed) / 0.70 from the PRs closed before this one was opened (0.5 when fewer than 5; uses any-time merges).

Note that `B1_prior` and `B2` use raw historical merge rates over PRs closed before the target PR opened (any-time merges), while the target label `y` counts merges within 90 days. B2 leaves out friendliness's first-reply (0.20) and activity (0.10) parts: neither can be rebuilt as of the day an old PR was opened without new API calls, so the weights are renormalized over the 0.70 that remains.

Best baseline on test AUC: **B1_prior**. Model minus B1_prior: -0.019 AUC, 95% CI -0.052 to 0.013. Lowest baseline Brier: B1_prior.

B0 and B1 turn into one constant per held-out project (the other projects' rate), so their pooled AUC only says that projects with a low rate elsewhere do well here; read B1_prior and B2 for this check.

## Verdict

The model is used only if all of these hold:

- PASS: test rows 335 >= 150, merged 127 >= 30, not merged 208 >= 30
- FAIL: test AUC 0.636 >= best baseline 0.655 + 0.03
- FAIL: 95% bootstrap lower bound of (model - best baseline) AUC -0.052 > 0
- PASS: test Brier 0.227 <= best baseline Brier 0.248
- FAIL: leave-one-project-out AUC 0.680 > best baseline 0.697

At least one check fails, so `beats_baseline` is false and **the score is not used**: `scout/mergemodel.py` refuses to load the file, and `rank.score_issue` gives exactly the scores it gave before the model existed, whatever `use_merge_model` says. The data keeps accumulating every night; retrain when there is more of it.

## What the model cannot know

- Whether the change is any good, fits the project's plans, or duplicates another PR.
- Reviews, comments, CI results, labels: nothing that happens after the PR is opened is an input.
- Who the author is beyond their earlier PRs in the sample, including whether a maintainer asked for the PR.
- Whether the issue was claimed, assigned, or discussed first.
- How the project behaves outside the window the sample covers, and for projects that merge outside GitHub.

## How to retrain

```sh
# rows accumulate in <data>/pr_outcomes.jsonl every night; to fill it now (about 4 GET requests a project):
python3 scripts/backfill_pr_outcomes.py --state <data>/state.json --out <data>/pr_outcomes.jsonl
python3 scripts/build_merge_dataset.py --rows <data>/pr_outcomes.jsonl --state <data>/state.json \
    --out /tmp/merge_dataset.jsonl --meta /tmp/merge_dataset_meta.json
pip install -r requirements-train.txt   # in a separate virtualenv; the scout itself never needs it
python3 scripts/train_merge_model.py --dataset /tmp/merge_dataset.jsonl --meta /tmp/merge_dataset_meta.json \
    --out <data>/merge_model.json --doc docs/merge-model.md
# preview the ranking change on a copy of the data (needs a passing model):
python3 scripts/before_after_merge_model.py --data <copy of the data>
```

A model file older than `merge_model_max_age_days` (default 90 in `targets.toml`) is ignored, so retrain at least that often if it is switched on.
